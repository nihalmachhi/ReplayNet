# Decisions

This file records the choices that shaped the dashboard, especially where the
reference design and the backend disagreed. Each entry states the decision, the
reason and the cost.

## 1. Port the reference layout instead of inventing a new one

**Decision.** Keep the structure, spacing, type scale and interaction model of
`TraceForge-v5__1_.html`, replacing only the project-specific content.

**Why.** The reference is a proven single-page marketing layout with a hero tour,
pipeline steps, an interactive simulator, results cards, a bento grid, quick
start, scope, FAQ and a flow diagram. Reusing it keeps the three DevOps sites
visually consistent and makes the port reviewable.

**Cost.** Some class names and section shapes are inherited even where the
content differs. The CSS is split into `tokens`, `base`, `layout`, `components`
and `animations` so the inherited rules stay readable.

**Reference copy.** The built reference DOM is committed at
`e2e/reference.html`. It is a reading aid and a visual baseline, not a runtime
dependency.

## 2. React 18 + TypeScript strict + Vite 5, no UI library or router

**Decision.** Use React 18.3.1, TypeScript 5.9.3 and Vite 5.4.21 with strict mode,
plain CSS and in-page anchors.

**Why.** The page is a single document with anchor navigation. A router would add
state and history for no benefit. A component library would fight the reference
styling. Strict TypeScript catches the fixture and engine shape errors that
matter most here.

**Cost.** Reusable widgets such as tabs and disclosures are hand-written. They
are small and covered by tests, so the maintenance cost stays low.

## 3. Reimplement CPython's MT19937 instead of approximating it

**Decision.** Implement CPython's `random.Random` seeding and `random()` path in
`src/lib/engine.ts`, and pin it with `new PythonRandom(7).random() ===
0.32383276483316237`.

**Why.** The page claims that seed 7 produces the same trial string as the
backend. With `Math.random()` or a simpler PRNG that claim would be false. Since
the trial draw is one comparison per trial, the full generator costs well under a
millisecond per run and makes the claim literally true.

**Cost.** About 90 lines of bit manipulation that must match a specific CPython
version's `init_by_array` and `random()` construction. The pinned draw and the
six pinned runs are the guard rails. A future CPython change to the seeding path
would be a deliberate port, not an accident.

## 4. Keep the engine pure and share it with the tests

**Decision.** Put Wilson, simulation, redaction, normalization, hashing,
hypotheses and minimization in `src/lib/engine.ts` as pure functions. The
simulator, results section and tests all call the same functions.

**Why.** A demo that hard-codes its own output can drift from the backend without
anyone noticing. A shared engine makes the fixtures executable documentation.

**Cost.** The browser engine has to reproduce backend quirks, including the
`sort_keys=True` JSON spacing and the reducer that removes every parameter.
Those quirks are documented rather than silently improved.

## 5. Copy expected values from Python, never from TypeScript

**Decision.** `EXPECTED_RUNS`, `WILSON_CASES` and `EXPECTED_DIGESTS` in
`src/data/fixtures.ts` hold values generated by running the Python backend, not
values printed by the TypeScript engine.

**Why.** A fixture generated from the implementation under test can only prove
the implementation is self-consistent. Copied values prove it agrees with the
source of truth. This is how the MT19937 port was validated.

**Cost.** Updating a failure rate means regenerating the fixture values with
Python. That is a feature: it forces the two sides to be checked together.

## 6. Use `useReducer` for the simulator

**Decision.** Model lab state as a reducer with explicit actions, and clear the
run on any control change.

**Why.** There are seven actions and several derived values. A reducer keeps
transitions atomic and makes the tests read like a specification. Clearing the
run prevents the worst UX bug in a measurement tool: showing a verdict that
belongs to a different scenario.

**Cost.** Slightly more code than local `useState` calls. The payoff is that the
state machine can be tested without rendering.

## 7. Derive results from fixtures, never duplicate numbers

**Decision.** `Results`, the comparison table and the tests all compute from
`SCENARIOS` via `runScenario`.

**Why.** The page claims "19 of 20 trials failed at seed 7". If that number were
typed into JSX, a fixture change would make the page lie. The tests pin the same
expectations independently.

**Cost.** The results section runs six scenarios at render time. Each run is 20
comparisons, so the cost is negligible.

## 8. Keep the slider at 5–100 in steps of 5

**Decision.** The repetition slider offers 5–100 in steps of 5, while the API
accepts 1–100.

**Why.** A range input with 100 integer stops is hard to hit precisely, and one
or two trials produce intervals so wide they teach the wrong lesson. The
comparison table also reads better at round numbers.

**Cost.** The dashboard cannot reproduce a 1-trial or 3-trial API run. The
`EXPECTED_RUNS` fixtures and the engine tests still cover arbitrary counts, and
the FAQ explains that a wide interval means a small sample.

## 9. Show the fixture's 422 instead of hiding it

**Decision.** The FAQ has an entry explaining that the committed sample bundle
ends with a blank line and returns 422 on upload. The dashboard uses cleaned
lines.

**Why.** A visitor will try the documented command with the documented fixture
and hit the error. Pretending it does not exist wastes their time. Naming the
cause turns a bug into a lesson about `splitlines()`.

**Cost.** The page admits a backend defect. That is the honest option, and
`BACKEND-NOTES.md` records it for whoever fixes it.

## 10. Label the lab as a toy, everywhere

**Decision.** Every place that shows a number also says the data is synthetic and
the simulator is a toy: the hero, the results note, the FAQ, the scope section
and the footer disclaimer.

**Why.** A 95% interval looks authoritative. Without the disclaimer, a reader
could reasonably conclude ReplayNet measured their network. It did not; it drew
one random number per trial against a hard-coded rate.

**Cost.** The page repeats itself. Repetition is cheaper than a false impression.

## 11. Keep the backend untouched except for documentation

**Decision.** Do not edit Python source. Record backend limitations in
`docs/BACKEND-NOTES.md` and adapt the demo honestly.

**Why.** The task is a dashboard port. Changing the service would require new
backend tests and could break the API contract. Documenting the gap is more
useful than quietly patching one side.

**Cost.** The demo works around the trailing blank line and the CORS origin list
instead of fixing them.

## 12. Accessibility is part of the port, not a later pass

**Decision.** Use semantic landmarks, one `h1`, ordered headings, real buttons,
labelled selects and inputs, `aria-pressed` on the timeline, live regions, a skip
link, visible focus and reduced motion from the start.

**Why.** Retrofitting accessibility into a visual port usually leaves gaps. The
reference already has a strong structure; the port keeps it and fixes the
heading-order issue in the footer.

**Cost.** The footer column headings are `h3` instead of the reference's `h5`.
The visual result is identical because the styles are class-based.

## 13. Test behaviour, not snapshots

**Decision.** Use Testing Library queries and engine assertions. Do not commit
component snapshots. Use Playwright only for browser-level smoke and visual
checks.

**Why.** Snapshots fail on harmless markup changes and hide intent. Behavioural
tests describe what the page must do.

**Cost.** Some structural regressions are only caught by the Playwright visual
spec. That is the right layer for them.

## 14. Coverage thresholds at 80/75

**Decision.** Enforce 80% lines, statements and functions, and 75% branches.

**Why.** The project brief asks for at least 80% overall and 90% on `src/lib` and
`src/data`. The suite currently clears both comfortably. A single global
threshold is simple to run in CI and in a pre-push check.

**Cost.** The threshold is a floor, not a target. Reviewers should still read the
coverage report rather than trusting the number.

## 15. Playwright visual checks with reduced motion

**Decision.** Run visual tests with `prefers-reduced-motion: reduce`, disable
animations and remove the SMIL flow dot before taking screenshots.

**Why.** Animated screenshots are flaky. Reduced motion makes the tour static and
the reveal immediate, so the captured pixels represent the layout rather than a
random animation frame.

**Cost.** The visual test does not prove that the animations work. The Vitest
tour tests cover the behaviour, and the smoke test covers the interactive states.

**Baselines are Windows-only.** They are committed for `win32` and the spec skips
on other platforms, because font rasterisation differs enough to exceed the 3%
pixel tolerance. CI therefore runs the smoke suite only.

## 16. Pin exact dependency versions and commit the lockfile

**Decision.** Every dependency in `package.json` is an exact version, and
`package-lock.json` is committed. CI uses `npm ci`.

**Why.** Reproducible builds and a reviewable dependency diff. Floating ranges
make a marketing site fail for reasons unrelated to its code.

**Cost.** Upgrades are explicit pull requests. That is intentional.

## 17. Deploy to GitHub Pages with a project base path

**Decision.** Build with `VITE_BASE=/ReplayNet/` and deploy `dashboard/dist`
through the Pages workflow.

**Why.** The repository is a project site, so assets must resolve under the
repository name. Local development uses the same default.

**Cost.** A user who opens `dist/index.html` from the filesystem sees broken asset
paths. The README points to `npm run preview` instead.

## 18. No claims beyond the backend

**Decision.** The copy says offline JSONL ingest, recursive redaction, UTC
normalization, seeded trials, Wilson intervals, evidence-linked hypotheses and
role checks. It does not claim traffic capture, protocol emulation, live devices,
calibrated probabilities, automated remediation or multi-process SQLite.

**Why.** The backend genuinely implements the first list and genuinely lacks the
second. The FAQ and scope sections state the gaps in plain language.

**Cost.** The page is less impressive than it could be. It is also accurate, which
matters more for a measurement tool.
